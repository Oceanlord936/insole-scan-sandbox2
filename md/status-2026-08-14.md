# Status & Plan — 2026-08-14

Documenting where the OpenCV-based foam detection stands before a deliberate
reset. Detection is still unreliable after a long chain of additions and
verification passes, and the accumulated modifications made it hard to tell
whether the core algorithm itself is the problem or something layered on top
of it. Resetting to a byte-faithful copy of the original source's algorithm,
rebuilding from there.

## Goal

Detect the insole foam's 4-corner outline live via the camera, as the first
step of "plan 2" (see `InsoleScanSandbox/md/08-12-2026-plan-cv-rotation-scan.md`):
a document-scanner-style live camera feed, foam rotated by hand between
captures instead of the camera orbiting the object.

## What was built, roughly in order

1. **`InsoleScanplan2` scaffolded** from a bare Android Studio template - two
   real build fixes hit and fixed: a stale Gradle daemon still pointing at a
   broken JRE (`--stop` fixed it), and `compileSdk 36` mismatched against
   newer `core-ktx`/`lifecycle-runtime-ktx` versions the template pulled in
   (pinned back to the same known-good versions `InsoleScanSandbox` uses).
2. **Bare CameraX preview + capture screen** (`camera/CameraScreen.kt`) as
   minimal scaffolding, no Hilt/Room/ViewModel.
3. **Studied the reference SDK** (`Document-Scanning-Android-SDK`, zynkware,
   downloaded locally) - a library + sample-app Gradle setup. Traced the real
   detection algorithm to `OpenCvNativeBridge.kt` (Canny-edge-based: blur ->
   normalize -> threshold -> normalize -> Canny -> threshold -> morphological
   close -> findContours -> convex hull -> approxPolyDP for a 4-corner
   polygon) and the live CameraX<->OpenCV wiring to `ScanSurfaceView.kt`.
   Confirmed the SDK's own live path targets ~400px-wide analysis frames
   (`IMAGE_ANALYSIS_SCALE_WIDTH`) - the algorithm's fixed-pixel kernel sizes
   assume that scale.
4. **`docscan/OpenCvNativeBridge.kt`** - ported, initially trimmed (removed
   the 5-corner "bent paper corner" reconstruction branch and the
   crop/perspective-transform methods, none needed for live-only detection).
5. **`docscan/DocScanScreen.kt`** - live CameraX preview + `ImageAnalysis`
   running the ported detector every frame, with a green/amber live outline
   overlay and explicit "Detected"/"Not detected" status text (the original
   sample app silently falls back to default corners on failure with no
   visible sign anything went wrong - deliberately avoided that here).
6. **Real bug found and fixed**: `org.opencv:opencv:5.0.0.1` (the latest
   Maven Central release) ships an `Imgproc` class missing `approxPolyDP`,
   `arcLength`, `convexHull`, and `contourArea` entirely (confirmed by
   decompiling the actual jar) - pinned to `4.9.0` instead, which has the
   full API.
7. **Real bug found and fixed**: `ImageAnalysis` had no target resolution
   set, so CameraX defaulted to a much higher resolution than the ~400px the
   algorithm's kernels were tuned for - detection was unreliable even against
   real A4 paper until this was set explicitly.
8. **Added on top, one at a time, each in response to real on-device
   testing**:
   - `CornerStabilizer.kt` - buffers recent detections, only shows a result
     once several consecutive ones land close together, to stop the raw
     per-frame jitter.
   - `ColorCheck.kt` - samples mean HSV inside a detected region as a
     confirmation stage on top of geometry (never calibrated against the
     real foam's actual color - stayed a placeholder guess the whole time).
   - Geometric guards added to `OpenCvNativeBridge.kt`: reject if any corner
     touches the frame's own edge (the camera view boundary is a perfectly
     stable false "edge" the stabilizer could lock onto), opposite-side
     length ratio, minimum area relative to the frame, maximum aspect ratio,
     and a "prefer whichever candidate sits closest to frame center"
     selection preference (not part of the original algorithm at all).
   - Accelerometer-based "is the phone face-down" pose check
     (`AccelerometerPose.kt`, same technique as `InsoleScanSandbox`'s
     validated `AccelerometerTilt.kt`) gating a foam-specific top-down
     aspect-ratio guard (`TopDownRatioCheck.kt`, ratio estimated from one
     reference photo) - **fully removed later** at the user's request after
     it was suspected (incorrectly, per code audit) of being "always on."
   - Every guard made independently toggleable from the UI, to isolate which
     one, if any, was over-rejecting.
9. **Verification passes performed, all confirmed clean**: the core Canny
   pipeline's constants and call order checked line-by-line against the
   original source - matches exactly, not corrupted. `DetectionOverlay`
   confirmed to render live detection data only, no hard-coded/fixed shape
   anywhere. Every shape constraint confirmed properly gated behind its own
   toggle, no hidden always-on path found.
10. Guard defaults flipped from all-ON to all-OFF, so the app would start in
    "universal any 4-edge shape" mode (matching the unmodified original
    algorithm) without needing manual toggling.

## Where it stands

Despite the above, detection is still reported as unreliable, and the report
persisted even after (10) reduced the live code path to something very close
to the original, unmodified algorithm. Two real possibilities remain
unresolved:
- The base Canny-edge algorithm itself may just not be reliable enough for
  this object/environment (low contrast, background texture, lighting) -
  this was flagged as a real risk from the start (see the color-vs-contrast
  discussion earlier in this project - Canny is a brightness-gradient
  detector, not a color detector, and was always expected to struggle
  against a background with similar brightness to the foam).
- Something in the accumulated modifications, despite every individual
  audit coming back clean, may still be interacting in a way that wasn't
  caught - hard to fully rule out given how many pieces had been layered on.

## Decision

Reset: remove all layered additions (stabilizer, color check, geometric
guards, toggles) and restore `OpenCvNativeBridge.kt` to an exact,
byte-faithful copy of the original source (including the parts trimmed
earlier - the 5-corner bent-corner handling, `getScannedBitmap`/
`getContourEdgePoints`/`getPoint`, `contourArea` - even though not all are
exercised by the live path, keeping the class a genuine unmodified copy
removes any doubt about what's actually running). `DocScanScreen.kt` reset to
the minimal version: live preview + raw per-frame detection + overlay, no
stabilization, no color check, no extra guards. The two real, narrow
integration fixes that aren't part of the algorithm itself - the OpenCV
4.9.0 pin and the ~400px analysis target resolution - are kept, since both
are corrections to match the original's own assumptions, not modifications
to its behavior.

## Next steps

1. Test the pristine baseline against real objects (plain A4 paper first,
   then the foam) and observe raw, unmodified behavior directly.
2. If even the pristine baseline is unreliable against paper (the
   algorithm's intended best case), that points at the base algorithm/
   environment, not any of the removed additions - worth revisiting the
   HSV color-threshold alternative discussed early in "plan 2" instead of
   continuing to patch the Canny approach.
3. If the pristine baseline works reasonably against paper but not the foam,
   that confirms the original contrast-vs-color concern, and color
   thresholding (this time calibrated against real measured numbers before
   relying on it) is the fix - add it back deliberately, one piece at a
   time, testing after each addition rather than layering several before
   the first real test.
